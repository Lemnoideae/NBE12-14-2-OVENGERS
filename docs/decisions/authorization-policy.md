# 기술적 의사결정 — 인가 정책

> 구현 기준: `d1a15ec` / 문서 갱신: 2026-10-21

## 문제 상황

로그인 성공 여부만 확인하는 인증으로는 "관리자만 공간을 등록할 수 있다", "본인 예약만 취소할 수 있다", "취소된 예약으로는 출입할 수 없다" 같은 규칙을 표현할 수 없다. 이 프로젝트는 인증·인가를 다음 다섯 축으로 확장하는 것을 핵심 목표로 삼는다(기획서 2-2).

## 인증·인가의 다섯 축

| 축 | 질문 | 예 |
| --- | --- | --- |
| 인증 | 이 요청은 어떤 회원의 인증 정보로 들어왔는가? | Access JWT와 DB 세션·회원 상태 검증 |
| 역할 기반 인가 | 공간 등록·수정, 전체 예약 조회를 요청한 회원이 관리자인가? | ADMIN 전용 API |
| 소유권 기반 인가 | 조회·취소하려는 예약이 본인 것인가? | 예약 취소, 도어 토큰 발급 |
| 상태 기반 인가 | 예약·토큰 등 대상 리소스가 해당 작업을 허용하는 상태인가? | 취소는 HELD 또는 시작 전 CONFIRMED, 도어 토큰은 CONFIRMED 또는 IN_USE |
| 시간 기반 인가 | 지금 출입 토큰을 발급/사용할 수 있는가? | 체크인 허용 구간, 종료 시각 전 |

## 선택 및 근거

- Access JWT의 서명·만료·회원 클레임·sid를 검증한 뒤 DB 세션의 회원 귀속, 만료·폐기 및 회원 ACTIVE 상태를 확인한다.
- 정지·탈퇴·비밀번호 재설정은 기존 세션을 폐기하며, 로그아웃은 해당 세션을 폐기한다. 이후 기존 AT로 보호 API를 호출하면 401 `INVALID_ACCESS_TOKEN`으로 차단한다. 인증 저장소 장애는 503이며 우회 허용하지 않는다.
- RT 재사용은 해당 로그인 세션과 RT를 폐기한다. 공통 인증 검증은 각 도메인의 역할·소유권·상태·시간 검증을 대신하지 않는다.
- 비활성 회원의 출입 검증 요청은 필터에서 차단하면서 별도 트랜잭션으로 DENY / MEMBER_INACTIVE 로그를 남긴다. 조건과 제외 범위는 [출입키 정책](access-key-policy.md)을 따른다.
- V3 Redis 인증은 실험 구현으로 보존하고 운영 도입을 보류했다(2026-10-21). dev 기준은 V2(DB)이며 상세 판단은 [V3 실험 결과](../testing/auth-v3-experiment-results.md)를 따른다.
- 역할은 `USER` / `ADMIN` 두 가지만 둔다(`MemberRole` enum). 팀별 역할, 공간 운영자 소유권 같은 추가 개념은 도입하지 않는다(예약은 항상 개인 명의).
- **관리자 권한은 소유권 검사를 대체하지 않는다** — 관리자도 본인 예약이 아니면 취소·출입 토큰 발급을 할 수 없고, 강제 취소는 별도의 `force-cancel` 경로로만 허용한다. 이것이 기획서가 명시한 핵심 차별점이다.
- 화면에서 버튼을 숨기는 것과 별개로, 모든 보호 API에서 서버가 권한을 검사한다(클라이언트 신뢰 금지).
- 일반 회원의 타인 예약 접근은 `FORBIDDEN_NOT_OWNER`(403)로 차단하고, 존재하지 않는 예약 접근은 `RESERVATION_NOT_FOUND`(404)로 처리한다.
- 회원가입 요청으로 `role`을 지정할 수 없다 — 서버가 항상 `USER`로 생성.

## 담당 간 협업

공통 인증(AUTHN/AUTHZ 필터)은 천종원이 제공하고, 각 도메인 담당자(space: 김재철, reservation: 이태호, credit_transaction/history: 백한비, door_access: 박창현)가 자신의 `AuthorizationService`와 관련 테스트를 구현한다(기획서 13장, 리스크 4). *(2026-09-15: `payment` → `credit_transaction`, `core-domain-decisions.md` §1/§11)*

## 검증 방법

- 일반 회원의 관리자 API 접근, 타인 예약 접근이 거절되는지 테스트.
- 관리자도 타인 예약 취소·출입 토큰 발급을 할 수 없는지 별도 테스트.
- 계정 정지 후 기존 AT 요청이 거절되고 세션 복구 없이 재사용되지 않는지 검증한다.
- 비활성 회원 출입 요청의 거절 로그와 체크인 미발생은 `InactiveMemberAccessFilterTest`, `InactiveMemberAccessIntegrationTest`에서 검증한다. 이번 문서 수정에서 테스트를 새로 실행한 것은 아니다.
- 세션 폐기 범위를 구분하여 검증한다. 로그아웃·RT 재사용은 해당 세션, 정지·탈퇴·비밀번호 재설정은 회원 전체 세션이 대상이다. 관련 회귀 기록은 [인증 보안 테스트](../testing/auth-security-tests.md)를 따른다.
